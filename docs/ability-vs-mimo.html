结论

一句话：同一个 DeepSeek-V4.1-Flash 下，两个 agent 的编程能力没有代际差距——MCode 16/16（100%），MiMo-Code 15/16（94%）；MCode 中位耗时 21s、MiMo 46s，MCode 快约 2.2 倍。
最重要的一条差异（此前被误读）：在第一轮评测中（题目本身有 bug 时），MCode 有 3 个会话没有直接交卷，而是发现评测题目本身有错，主动调用 question 工具向用户报告并等待决策。它指出的问题与我事后手动修复的完全一致：
① 「test/solution.test.js 里没有 import { debounce }，每个用例都抛 ReferenceError，任何 solution.js 的写法都不可能通过」
② 「用例 1m1d 的期望值 87060 与其它用例矛盾，应为 86460」
这不是卡死，是正确的工程行为——遇到不可能满足的题目时停下来问，而不是硬编一个假答案骗过判分。MiMo 在同一批任务里也读到了这些错误（bash 输出里有同样的 ReferenceError），但它的工具集只有 bash/read/write/glob/edit，没有向用户提问的通道，于是只能自行绕过。
题目修好后重跑这 3 个会话，MCode 全部直接完成（54s / 59s / 101s），不再需要提问——说明它提问是因为题目真的有问题，而不是偷懒。
  • 能力层面：唯一失败样本是 MiMo 的 T5#1 防抖 leading 模式（同一任务第二轮就通过了），属单点失误而非系统性缺陷。
  • 速度层面：MCode 大多数任务 13–25 秒收工；MiMo 普遍 24–209 秒，倾向反复自查、跑测试后才收尾。同样交付正确结果，MCode 的交互响应更干脆。
  • 工程素养层面：MCode 会识别「题目本身不可能通过」并上报，MiMo 不会。在真实项目里这意味着——需求写错时，MCode 会来问你，MiMo 会默默猜一个方向做完。
  • 推理服务本身是干净的：此前观察到的 1500+ 次「连接拒绝/断流」根因是我这边的评测通道——环境里的 HTTP_PROXY 让 MiMo 发出绝对 URL 请求、被本地重试代理拼成非法地址。去掉代理变量直连后，MiMo 16 个会话零故障、最快 24 秒完成。
评测工装修正（4 处，均已验证）：① 任务里的 npm test 原为 node --test test/，在 Node 22.22/25.9 上把目录当模块解析直接报错，导致任何解法都判 FAIL；② T1 隐藏测试把 1m1d 的期望值写成 87060（正确为 86460）——MCode 自己发现了这条；③ T5 测试缺少 import { debounce }，导致永远失败——MCode 也发现了这条；④ 判分改为「洁净目录 + 原始测试」，避免 agent 改动测试文件骗过判分。修正后 stub 基线全部失败、参考实现全部通过，判分有区分度。
顺带修掉的一个真实缺陷：既然 MCode 会在题目有错时提问，那么「没人回答」就必须有出路。此前 question 工具会无限期等待——窗口关掉、崩溃、或无人值守跑批时，整个 turn 永久挂住。现在加了 30 分钟上限，超时按「用户跳过」处理（返回 Unanswered 让模型继续），不再挂死。
