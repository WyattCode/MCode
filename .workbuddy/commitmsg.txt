feat(android): the +/- counter is one capsule with two halves

The reference's edited-files row ends with a single object: a green half for the
lines added and a pink half for the lines removed, meeting at a hard edge with no
gap and no divider between them. Sampled off its own thread - 17.6 tall, halves
(210,230,212) and (234,206,215), text (76,156,73) and (212,136,160).

This app drew two bare monospace labels six apart in #1A7F37 / #E5484D. Two
unrelated figures, rather than one change with a size - which is what the row is
reporting.

`DiffCounter(add, del)` now draws the plate, with only its outer corners rounded
so the shape reads as one object. Both call sites use it: the turn's edited-files
summary and each file's own row. Dark gets its own four values rather than
reusing the light ones, since a #D2E6D4 fill would glare on the near-black page.

Confirmed on the pad in a thread that really has edits: 「已编辑 2 个文件」 ends in a
green +12 plate, and each file row with a +6.

Two things this pass did **not** settle, both now recorded:

- The **diff line colours** inside an expanded patch (#20A923 added, #E5351C
  removed) are still the desktop's. Every patch in the reference thread on this
  machine is reached through a collapsed group, and opening one to read line
  colours needs a tap I did not get to land.
- The reference's counter carries a **chevron** after it, opening the file list.
  This app shows the list inline instead, so there is no chevron to draw.

Also learned the hard way, and now in the notes: `input text` will not take
spaces across separate calls on this device — it strips them and welds the words
together. One call with `%s` for each space works, and old text has to be cleared
from the end first or it prepends.
