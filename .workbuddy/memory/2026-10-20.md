## 代码二次审核（`7eff5e8e`）——6 个 bug

1. **`loadingThread` 卡死**：只在成功路径清，超时/失败走 `?: return@launch` 直接返回 → 界面永久停在「正在加载对话…」。修：`try/finally` 清除。
2. **`waiters` 泄漏**：只在收到回包时 `remove`，超时的请求永久留在 map（每次交互累积）。修：加 `forgetResponse(id)`，在 `rpc` 的 finally + 4 处手写 `awaitResponse`（session.get / command.list / file.listDir）里调用。
3. **已答权限复活**（影响最明显）：`pendingPerms` 从不在回答后移除 → 重开该会话时已批准过的权限**再次显示为待确认**，行的胶囊也一直亮着。修：`clearPerm()`，从 respondPerm / respondPermReason / answerQuestion 调用。
4. **`currentSession!!` 4 处**：队列消息的发送/撤回、输入框发送都硬断言。切走会话后点击 → NPE。goalResend 还在两次 rpc 之后重读 currentSession，可能把**错误的会话**标成运行中。
5. **`session.deleted` 残留**：id 永久留在 `unseen`；pendingPerms/pendingQuestions 也不清。
6. **`projectRows` 性能**：`sessions.count{}` 在 `projects.map{}` 里 → O(n×m)，排序里还有 `projects.indexOf`。改单遍建表。

**Kotlin 局部函数限制**：同一函数内的局部函数**不能前向引用**（`respondPerm` 调用定义在后面的 `clearPerm` 会 Unresolved reference）。要么移到前面，要么抽成类的成员函数。

**判断澄清**：`complete()` 在 OkHttp 线程调用是**安全的**——协程由 `rememberCoroutineScope()` 绑定 Main，恢复时自动回主线程。不要误判为线程 bug。

## 断线重连（`367cfd16`）

- **原来完全没有重连**：`onFailure` 只把 `connected=false` 就停了。断一次就得手动进「连接设置」点连接，而且界面症状只是「列表空了」，看起来像没会话而不是断线。
- 加了退避重连：1s → 2s → 4s → 8s → 之后每 15s，成功后 `retryDelay = null`。
- 加了断线条「连接已断开，正在重连…」。**关键坑：必须抽成独立 `OfflineStrip()`**——宽屏（平板，也是唯一运行形态）的左右两栏各自画头部，**根本不调用 `AppTopBar`**，只在 AppTopBar 里加的话平板上永远看不到。
- 验证方式：app 运行时 taskkill 掉网关 → 断线条出现、日志两次重试失败 → 启动网关 → 10 秒内自动恢复、列表回来。

## 协议错误处理（`faf05ba4`）

- **`rpc` 从不检查 `ok`**：协议对任何拒绝都回 `{ok:false, error:"..."}`，但 34 处调用方只读 `data`，`null` 被当成"没有内容"。被拒绝的请求和空结果在界面上完全一样。现 `rpc` 把 `lastError` 记下来，头部下方出红条。
- **为什么不直接 throw**：大量调用在 `scope.launch` 里没有 catch，直接抛会把"静默失败"换成"崩溃"。所以只记录，另给 `rpcOrThrow` 供需要内联处理的调用方用。
- **`ProjectLocations.assert` 不是 bug**：`canonicalDirectory` 会向上找最近的真实祖先再拼回去，这是桌面端允许"项目文件夹稍后再建"的设计。但**手机端手输路径**必须自己校验，否则打错字就多一个指向空的项目行。加了 `file.listDir` 前置检查 + Toast。
- **测错误路径的方法**：故意发不合法请求（`session.get` 用随机 id / `project.add` 用不存在路径），看服务端回什么、界面怎么反应。这一招这轮抓到两个问题。

## 重连后的状态一致性（`2651c670`）

- **`session.list` 只重建了 sessions + pendingPerms，没重建 `unseen`**：断线期间跑完的轮次没有任何会话事件送达，`unseen` 因此永远是空的 → 那些回复和"已看过"完全无法区分。现按 `row.updated > lastSeenAt` 补标。
- **首次连接必须跳过**：`lastSeenAt` 初值 0，不加判断的话第一次启动所有会话都会被标未读。用 `if (lastSeenAt > 0)` 区分首次/重连。
- **`currentSession` 指向已删会话**：`sessions.clear()` 后列表是权威，但没人检查当前会话还在不在 → 面板显示一个没标题、没正文、发送失败的会话。现加 `gone` 检查并连带清理 unseen/pendingPerms/pendingQuestions。
- 验证：首次启动零蓝点；杀网关→断线条→重启网关→12秒内自动恢复且无假蓝点。

## finish 语义（`c90e4f65`）

- **`finish` 五值**（`end_turn / max_tokens / aborted / error / refusal`），手机端只判断「非空」来决定是否还在运行，**完全不看值**。后果：被 `max_tokens` 截断的回复看起来就是正常结束，error/aborted 的轮次静默收场。
- `Item.Msg` 加 `finish` 字段，四种非正常结束各给一行提示。
- **关键坑**：第一版把提示放在 `item.text.isNotBlank()` 分支里，但实测发现 `error` 轮次 **textLen=0**——压根进不了那个分支，提示永远不会出现。必须移到分支外。
- 查真实数据的方法：连网关发 `session.get`，统计 `messages[].finish` 分布，找 textLen=0 的样本验证边界。
- **reasoning part 仍被主动跳过**（不显示模型思考）。PC 的 `thinkOnly()` 是「有思考但无正文 → 算失败」，手机端目前把它当空回复，暂未处理（低优先级）。

## 空轮次不渲染的根因（`1bd8cebe`）

上一轮加的 finish 提示**完全没生效**，两次改都"看起来没用"。根因有两个，都是实测才暴露的：

1. **`upsertMessage` 的准入条件把空 assistant 轮次整个丢掉**：`if (body.isNotEmpty() || role == "user" || images.isNotEmpty())`——error/aborted 轮次 textLen=0 且非 user，压根不建 Item，提示无处附着。改成额外放行「finish 非 end_turn」或「有 reasoning」的 assistant 轮次。
2. **`fallback = "…"` 让空回复看起来非空**：这个省略号本意是给「只发了文件、没写字」的用户轮次，但无差别应用到了 assistant，导致 `text.isBlank()` 恒为 false。

**方法论教训**：改 UI 提示类逻辑前，先用 `println` + logcat 确认「数据有没有到达渲染层」，再怀疑渲染条件。我这次连续三次改同一处都没生效（提示放分支内 → 放分支外 → 放宽 finish 条件），每次都在猜渲染逻辑，直到打印 `blank-assistant` 计数为 0 才定位到**根本不建 Item**。

**thinkOnly**：PC 的 `thinkOnly()` = 结束了 + 有思考 + 无正文 → 算失败。已实现（reasoning 只计数不渲染）。

## 模式扫描（`c068ffdf`）

## 自查我自己的改动：重连有两个 bug（`2ffa515a`）

上上轮的"退避重连"其实**根本不会退避、还会彻底放弃**——是我自己引入的：

1. **退避从不增长**：`onState(false)` 里无条件 `retryDelay = 1000L`，而每次重试失败都会再触发 `onFailure` → 每次都重置回 1 秒。等于固定 1 秒轮询。
2. **到上限就永久停**：`LaunchedEffect(connected, retryDelay)` 以 retryDelay 为 key，退避涨到 15000 后不再变 → effect 不再重启 → 重试彻底停止。**实测证据**：最后重试 07:06:31，07:07:46 仍断线，而网关全程在监听。

修法：改成 `LaunchedEffect(connected)` + `while (!connected && ...)` 循环；`retryDelay` 只在为空时初始化。

**验证**：2s → 2s → 4s → 8s → 15s 持续不停；网关回来 25 秒内自动恢复。

**教训**：`LaunchedEffect(keys)` 的 key 里不能放"会被 effect 自己修改且会收敛"的状态——一旦收敛就不再触发。这种 bug 只在「持续失败超过上限时长」时才暴露，短测发现不了。要测退避必须跑到上限之后。

## 多 text part 覆盖 bug（`bdb78eea`）

- 协议允许一条 assistant 消息有**多个 text part**（写作 → 调工具 → 继续写）。PC 的 `replyText` 用 `\n\n` 连接全部。手机端 `"text" -> copy(text = part.text)` 是**覆盖**，只会留最后一个 part → 用过工具的回复只显示后半段。
- 修法：`partTexts` 按 part id 存，`partOrder` 记首次出现顺序，每次重建整段。
- **现实样本**：扫了 18 个会话，**没有一条**多 text part 的消息。所以是「协议允许但当前没触发」的防御性修复。但覆盖写法本身是错的——它依赖这个形状永不出现。
- 同时确认了几处安全的写法：`LaunchedEffect(search)` 双重校验 needle；`toTop` 计数器；`copy(text=...)` 会自动保留 finish/thought 字段。

## 自查状态管理（`ed7c0138`）

又两处是我自己引入的：

1. **卡片可能永不消失**：`clearPerm` 只清 map，靠服务端 `permission.resolved` / `question.replied` 移除界面卡片。但服务端 `respond()` 里 `if (!pending) return` —— 请求已不在 pending 时**静默返回且不发事件**（桌面端先答过、或重连后重放旧卡片）。这时手机端发送成功、无事件回来、卡片永久留在页面上。修：`clearPerm` 自己移除行。
2. **未读误报**：重连补标用 `row.updated > lastSeenAt`，但 `lastSeenAt` 只在**整个列表重建**时更新。用户中途打开看过某个会话，重连后它仍被判定为"有更新"→ 误报蓝点。改用 `seenUpdated[会话]`（打开会话时记录、列表到达时更新）。

**方法论**：这两处都是「靠外部事件清理本地状态」的典型坑——外部事件**不保证到达**。凡是 `X 发生了 → 等事件 Y 来清理` 的模式，都要问一句「Y 一定来吗」。

**验证**：打开会话 → 杀网关 → 重启网关 → 25 秒内重连，断线条消失、列表**零误报蓝点**。

## 历史路径没填 partTexts（`451acb24`）

上一轮加 `partTexts` 时只改了**实时路径**，历史加载那条循环还在用 `text.append()` 且不写 `partTexts`。

**后果（比原 bug 更严重）**：打开一个历史会话 → 继续对话 → 新 part 流进来 → 重建只认得新 part → **整个气泡的历史正文被抹掉**。这是「打开旧会话接着聊」的常见场景。

同时统一了分隔符：历史是 `\n`，实时是 `\n\n`（PC 也是 `\n\n`）。

**先查了真实数据再改**：存盘消息**没有 `message.text` 字段**（len=0），只有 parts——所以 parts 循环是正文的唯一来源，两条路径都必须写同一个 store。

**模式**：一份数据有两条写入路径（实时 / 历史）时，加共享 store 必须两边都改。这类「只改了一半」的 bug 不会立刻报错，要等到两条路径交汇时才炸。

## seenUpdated 的两个遗漏（`185e808a`）

1. **从不清理**：会话删除后 `seenUpdated` 里的条目永久留着。两条删除路径都补了 `remove`。
2. **当前会话的记录不跟随**：记录「读者已看到哪个版本」的那段只在 `row.updated > seen` 时写，而正在看的会话每轮都在更新 —— 只有打开那一刻记录过一次。重连时就拿旧值比较，可能把**正在读的会话**标成未读。改成当前会话每轮都记录。

**模式：给状态加一个「按会话 ID 索引的 map」时，必查三件事**：① 会话删除时清 ② 当前会话是否特殊处理 ③ 是否有第二条写入路径。

**端到端验证**：打开会话 → 杀网关 → 重启 → 25 秒内重连、断线条消失、会话保持打开、无未读误报。

## Office 查看器（`d2ffe2b2`）

**方案**：本机没装 LibreOffice（PC 端靠它转旧格式），所以走 **jszip 手工解 OOXML → HTML**，服务端 `src/server/office/html.ts` 生成自包含页面（图片内联 data URL），手机端 WebView 显示、JS 关闭。

- docx：段落/标题/列表/表格/内联图片/粗斜体下划线
- xlsx：多 sheet 表格，sharedStrings 与 inlineStr 都支持
- pptx：按 sldIdLst 顺序的幻灯片栈
- 协议新增 `office.render { root, rel } → { path, kind, html, error? }`

**实文档实测挖出的 5 个 OOXML 坑**（读规范猜不到，只能转真文件）：
1. **列表两种写法**：`numId` 指向 numbering.xml，**或**样式名 `ListBullet`/`ListNumber`（深度用数字后缀）。Word 自己的模板用后者 → 只认 numId 会把所有列表变成普通段落。
2. `Title` 是独立样式，不是 `Heading1`。
3. **rels 的 `Id`/`Type`/`Target` 顺序不定**，标签中间还可能夹 `xmlns:` 声明 → 一个跨标签的正则必炸。逐个属性单独读。
4. **`Target` 可能是绝对路径** `/xl/worksheets/sheet1.xml` → 再按目录拼会得 `xl/xl/...`。用 `resolvePart(base, target)` 统一处理。
5. **单元格文本是 XML 转义的**（`&#22320;` = 地），且 xlsx 可能用 inlineStr 而非 sharedStrings → 不先 `decodeXml` 就 escape，会打出 `&amp;#22320;`。

**验证**：三种格式都过协议 + 真机截图（docx 标题+列表+表格+加粗、xlsx 两 sheet 中文表头、pptx 两页）。
